# 真机标定与部署准备

开始现场操作前，先阅读[离线真机准备审计](../../records/hardware/deployment-preparation/s19-readiness.md)及其[机器记录](../../records/hardware/deployment-preparation/s19-readiness.json)。审计只证明文件和软件接口准备完成；下面所有实物状态仍须逐项测量并留档。

当前只完成准备，不执行刷写、改 ID、标定或电机动作。机器人已装配，Arduino App Lab 已由用户安装；通信、机械中心、方向和 IMU 尚未实测。本页供仿真阶段验收后逐项操作，完成一项再记录一项。

## 1. 固定文件与记录

官方运行说明以本项目归档的 [README](../../workspace/official-reference/b401d85d20bb5bfd0237242a8a5ab6847fc962a2/README.md) 为准；源码提交为 `b401d85d20bb5bfd0237242a8a5ab6847fc962a2`。该增量归档目前只含更新后的行走模型，不能把它当作包含全部动作模型的完整可安装包。后续部署前应补齐同提交的文件与模型并校验清单；保留原完整归档作为回退基准。

每次板端操作建立 `records/hardware/<日期>/`，保存源码提交、模型 SHA-256、运行设置、原始状态日志、机械中心照片和结果。填写[逐舵机记录表](../../configs/hardware/commissioning_record_template.csv)，不把未测值写成通过。

## 2. 首次通信

在 App Lab 打开经校验的运行工程。官方说明要求首次下载板端库后停止应用，在 UNO Q 上的工程终端依次运行：

```bash
python3 tools/prepare-bridge.py
sudo bash tools/router-2m.sh
```

然后在 App Lab 点击 Run，打开它显示的地址，通常为 `http://<board-ip>:9527`。保留 **Inference only**，观察 **Servos online 15/15** 和 **IMU online**。Bridge 的 2 Mbps 与舵机总线的 1 Mbps 是不同链路。接线位置按归档说明和实际扩展板核对，不根据线的排列推断关节 ID。

现有[只读状态采集脚本](../../scripts/validation/capture_board_status.py)只访问 `GET /api/status`。后续在可见终端使用实际地址，先运行 `--help` 确认选项，再记录连续状态。它能核验反馈、推理计数与时间，不能证明机械零位或实际电机已经卸载；卸载状态还要现场确认。

## 3. ID、中心与方向

官方总线顺序为左腿 10–14、右腿 20–24、颈头 30–33、嘴 34。策略只有 14 个输出，顺序为左腿 → 颈头 → 右腿，嘴独立控制。完整下标对应见[策略关节表](../../configs/hardware/policy_joint_mapping.csv)。

1. 逐个对照实物标签和扫描 ID。需要改 ID 时按官方要求一次只接一个舵机，修改后重新扫描；整机 15/15 在线不能排除接错关节。
2. 在 Servo setup 中先 Read 并保留读数与照片。不要直接覆盖增益；当前归档不会在启动、使能或校准时替腿部和头部自动设置 KP/KD。
3. 依据官方装配图确定各关节机械中心。不能把模型 HOME 当作机械零位：例如行走 HOME 中髋俯仰约 22°，不是编码器中心。
4. **Reset Mid**：卸载状态手动摆到机械中心后重置中心，之后仍卸载。**Set center & hold**：在 Calibration 中设置中心并保持该关节，其余关节卸载。两种按钮的动作不同，操作前确认当前页。
5. 每个关节记录设置前读数、中心参考照片、设置后读数及重新上电后的读回。未能确认装配中心时先解决机械参考，不能用一个猜测角度代替。
6. 后续受控小幅验证时逐关节比较“正向目标—实际运动—位置反馈—速度反馈”的符号。全部通过后才进入整机 Default pose。观察期间准备使用 Torque off；离开 Control 页面只停止行进，仍可能保持力矩。

固定源码中 15 个舵机的 `MOTOR_SIGN` 均为 −1。这是该硬件约定，不等于本机已经核验方向。固件位置换算中心为 2047，校准保持值为 2048；位置换算使用 4095，速度换算使用 4096。先保持源码语义并记录量化差异，不自行把这些常量统一。

## 4. 更换顺序的修改范围

| 变化 | 修改内容 | 是否需要重新训练 |
| --- | --- | --- |
| 线缆串接次序变化，ID 和物理关节不变 | 核对通信与线束；按 ID 读取，不按接线先后读取 | 通常不需要 |
| ID 重新分配 | 同步维护 MCU ID 表、主机总线表、策略 ID 表、网页标签和日志解释 | 物理映射完全等价时通常不需要 |
| 电机方向相反 | 目标、位置反馈、速度反馈同时转换；检查限位方向 | 等价坐标转换可不重训，机械变化另评估 |
| 零位或装配偏差 | 逐关节偏移与范围；确认观测和目标使用同一变换 | 先标定；明显超出训练分布时再训练 |
| 型号、传动比、安装几何或时延变化 | 更新模型与执行器参数，重新做系统辨识和仿真对照 | 通常需要重新验证，可能重训 |

对单个关节，若策略角 `q` 与硬件角 `p` 的关系为 `q=s·(p−b)`，则目标为 `p=b+s·q_target`，速度为 `dq=s·dp`，其中 `s` 为 ±1。动作目标还要先恢复模型 HOME 与 action scale；不能只重排网络输出而保留旧观测顺序。嘴 ID 34 不得误插入 14 维策略向量。

已用固定源码离线核验 100 组随机数据和总线排列：关节对应、位置/速度符号及往返量化检查通过，见[核验结果](../../records/hardware/deployment-preparation/mapping-check.json)。这证明软件映射关系，不代表实物标定完成。

## 5. IMU 与时序

归档主机代码先把传感器向量变为 `[z, −x, −y]`，再应用 IMU 安装偏差补偿。机器人水平静止时策略重力投影应接近 `[0,0,−1]`。先做静止、俯仰和侧倾三个方向的记录，再填写偏差；仅靠重力不能确定偏航偏差。

设计频率是策略 50 Hz、反馈 100 Hz，仿真控制周期 20 ms。板端验收应记录接收、推理、发送计数随时间的增长，以及反馈年龄、序号缺口、坏帧、超周期和 MCU 诊断，分别报告中位数与高分位延迟。源码的反馈超时 150 ms、IMU 过期 500 ms 等是失联边界，不能当作理想运行延迟。保持电机卸载先验证断连与重连状态；断连后不得自动恢复使能。

## 6. 模型替换与回退

先保存原模型、配置和源码哈希，再检查候选的观测语义、关节顺序、HOME、action scale、动作历史、滤波和控制周期。61 维输入与 14 维输出相同只是必要条件。滚翻角度观测占用原填零位置的方案必须配套运行接口。

本轮离线审计进一步确认，归档运行程序让起身和滚翻共用约 22° 的腿部 HOME，而两模型元数据分别约为 20°、24°；起身等待 1 秒、滚翻 1.9 秒后切回，也与任务仿真参照不同。应先在同一仿真物理环境中比较运行程序语义与模型坐标适配，再决定后续板端设置；本轮不直接修改归档或真机。逐模型差异、动作历史和连续切换步骤见[技能切换准备](skill_switching.md)。

完成仿真验收后，先用 Inference only 比较候选与官方模型的目标和时序，再依次验证受控默认姿态、站立与低速行走。起身和滚翻在行走及各自仿真条件通过后单独验收。保存每次结果；出现异常时卸载，恢复已知模型与设置，重启后再次核对哈希和只读状态，不把“换回文件”直接等同于恢复完成。

新增接力组件仍属于仿真候选。站立接力使用共同的观测噪声、各自HOME与独立原始动作历史，并在5秒后投影目标及限制目标过渡。2rad/s尚未按本机舵机和反馈时序验证，旧请求越界时也不是瞬间消除越界；不能直接把该设置写入板端并视为部署通过。实际边界、输入差异和连续仿真协议见[切换准备](skill_switching.md)。

当前尚无可交付真机的自训模型；本页和离线表格属于部署准备成果。
